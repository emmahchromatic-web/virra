# Virra Site Design Spec
**Date:** 2026-05-01
**Status:** Approved — ready for implementation

---

## Overview

A holding page and content-marketing blog for **Virra**, a premium health and fitness app targeting women aged 20–40. The site's dual purpose: capture email signups pre-launch and drive organic traffic via health/fitness/nutrition blog content.

**Stack:** Astro · Decap CMS · GitHub Pages · GitHub Actions

---

## Site Structure

| Route | Purpose |
|---|---|
| `virra.app/` | Holding page — email waitlist capture |
| `virra.app/blog` | Blog index — grid of post cards |
| `virra.app/blog/[slug]` | Individual blog posts |
| `virra.app/admin` | Decap CMS editor (GitHub OAuth) |

## Content Schema

Each blog post is a Markdown file in `src/content/blog/` with the following frontmatter:

```yaml
---
title: string           # Required. Post headline.
excerpt: string         # Required. Max 200 chars. Used on index cards + <meta description>. Never shown in the article.
hero_paragraph: string  # Required. Max 400 chars. Reader-facing TLDR. Rendered at top of post in display font.
cover_image: string     # Required. Path to image in /public/images/blog/.
category: enum          # Required. One of the locked list below.
tags: string[]          # Optional. Freeform, comma-separated.
author: enum            # Required. One of the locked author list.
published_date: date    # Required. ISO 8601. Defaults to now in CMS.
---
```

**Locked category list:**
- Fitness
- Nutrition
- Performance
- Wellbeing
- App Updates

Writers select from this list only. No ad-hoc categories. This enforces consistent navigation, filtering, and SEO taxonomy.

**Excerpt vs hero_paragraph — the distinction:**
- `excerpt` is machine-facing: powers index cards, Open Graph descriptions, and `<meta name="description">`. Writers should write it like a search result snippet — factual, keyword-aware.
- `hero_paragraph` is reader-facing: appears at the top of the article body in a distinct display font. Writers should write it like a magazine standfirst — tone-setting, human, invites reading on.

## Decap CMS Configuration

**File:** `public/admin/config.yml`

Key settings:
- `publish_mode: editorial_workflow` — posts go through Draft → In Review → Published states before triggering a build. Draft posts live in a `cms/posts` branch and are invisible to the public.
- `media_folder: public/images/blog` — uploaded images land here.
- `public_folder: /images/blog` — the public URL path Astro will use.
- Backend: GitHub OAuth via Decap's hosted auth gateway (no separate auth server needed, free).

Writers access the editor at `virra.app/admin`. They log in with their GitHub account. Only GitHub accounts with repo access can publish.

## Deployment Pipeline

**File:** `.github/workflows/deploy.yml`

```
Trigger: push to main
Steps:
  1. Checkout repo
  2. Setup Node 20 + pnpm
  3. pnpm install
  4. pnpm astro build  →  outputs to dist/
  5. Deploy dist/ to gh-pages branch (peaceiris/actions-gh-pages)
```

GitHub Pages serves the `gh-pages` branch at `virra.app`. Build time: ~20–30 seconds. Every CMS publish creates a commit to `main`, which triggers this pipeline automatically — writers never interact with the deployment.

**Branch structure:**
```
main        ← source of truth; every push triggers a build
gh-pages    ← auto-generated build output; never edited manually
cms/posts   ← Decap CMS draft posts staging branch
```

**Custom domain:** `public/CNAME` contains `virra.app`. DNS configuration at the registrar:
- Four A records pointing to GitHub Pages IPs: `185.199.108.153`, `185.199.109.153`, `185.199.110.153`, `185.199.111.153`
- One CNAME record: `www` → `<github-username>.github.io`

## SEO

All SEO is handled in `BaseLayout.astro` via props — no external plugins beyond `@astrojs/sitemap`.

| Signal | Implementation |
|---|---|
| `<title>` | Post `title` field |
| `<meta name="description">` | Post `excerpt` field |
| `og:title` | Post `title` |
| `og:description` | Post `excerpt` |
| `og:image` | Post `cover_image` |
| Canonical URL | Astro `Astro.url` — auto-set per page |
| Sitemap | `@astrojs/sitemap` — regenerated on every build |
| Reading time | Calculated from word count in `[...slug].astro`, exposed as a display variable |

## Blog Post Layout

The `BlogPostLayout.astro` renders in this order:

1. **Header** — site nav with logo (placeholder until brand kit supplied)
2. **Category + reading time** — small label row
3. **Title** — display font (brand kit TBD)
4. **Hero paragraph** — distinct display font, larger than body, acts as TLDR standfirst
5. **Cover image** — full-width
6. **Body** — Markdown content, styled via `global.css` prose rules
7. **Tags** — at end of body
8. **CtaBanner** — "Virra is coming. Join the waitlist." with email form — appears on every post

## Holding Page

The approved Option 1 editorial design (`option-1-editorial.html`) is ported into `src/pages/index.astro` with the following adaptations:
- Inline `<style>` moved to `global.css` and scoped component styles
- Email form wired to **Formspree** (free tier, no backend required — form POSTs to Formspree endpoint, submissions visible in dashboard and forwarded to a specified email)
- Logo placeholder replaced when brand kit is supplied
- Font choices (`Cormorant`, `Outfit`) retained unless overridden by brand kit
